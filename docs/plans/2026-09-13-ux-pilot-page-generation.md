# UX Pilot as a second page designer

Design note, 2026-09-13. Ideation only; nothing here is implemented on this
branch.

## The decision in one paragraph

Forge keeps one way to store a page and gains a second way to produce it. A2UI
(the "Forge UI Designer") composes pages from the component catalog, as it does
today. A new UX Pilot agent asks UX Pilot to generate each page instead. Smith
asks the user which they want. Both agents write the same `pageLayouts`
artifact, pass the same catalog gate, run through the same converter and render
through the same engine. Nothing downstream of page layouts knows which one ran.

## What the user sees

After page contracts exist and before page layouts run, Smith presents a
two-card choice:

- **Forge UI Designer.** Composed from the component library. Consistent across
  pages, wired to the data model by construction, no external cost.
- **UX Pilot.** Screens generated by UX Pilot, editable in the user's UX Pilot
  workspace, re-synced by Forge. Spends the user's UX Pilot credits; the card
  shows the estimate for this app's page count.

Smith records the answer as a Blueprint decision. The user can later override
it per page in conversation ("redraw the dashboard with UX Pilot", "keep the
settings pages plain"), which becomes a per-page value on the same decision.

If the user picks UX Pilot and the organisation has no UX Pilot configuration,
Smith asks for it before the run, the way it does for Figma: the **name** of the
environment variable holding the key, never the key itself (§42), and
optionally the MCP endpoint.

## Where the choice lives

In the Blueprint, not in configuration or a flag. Two fields, declared in the
zod source and regenerated before any producer writes them:

- `decisions[]` gains a `uiDesigner` decision with value `forge` or `uxpilot`.
  This is the app-wide default.
- `PageContract.designedBy` (optional, `forge` | `uxpilot`) is the per-page
  override. Absent means "follow the decision".

The `page_layouts` node stays the **single producer** of `pageLayouts`. It
resolves the effective designer per page and dispatches to the A2UI author or
the UX Pilot agent. There is no second node writing the same section; the
dual-producer problem that stalled the earlier research branch is avoided by
keeping dispatch inside one node.

## MCP configuration

When the decision is `uxpilot`, the system uses the UX Pilot MCP configuration
already defined for design-source import on `claude/uxpilot-on-smithv2`:

| Key | Scope | Purpose |
|---|---|---|
| `UXPILOT_API_KEY` | organisation, write-only | resolved by name at call time, discarded after |
| `UXPILOT_MCP_URL` | organisation, optional | defaults to `https://mcp.uxpilot.net/mcp` |

Both live in the integrations registry beside the Figma keys, so they surface
in the same settings UI, use the same encryption, and are resolved by the same
secret resolver. Every call goes through the UX Pilot gateway: one controlled
hop that owns authentication, the allowed tool list, request logging, rate
limits and error classification.

The gateway's allowlist today is read-only by design, because generation spends
credits. This note changes that rule in one specific way: the generate tools
become allowed **only for a run whose decision is `uxpilot`**. The user's click
on the card is the consent. A run whose decision is `forge` cannot reach a
generate tool even if the key is configured. Import of a design the user drew
by hand stays read-only exactly as before.

Tool argument names are still discovered from the server's input schema at
session start rather than hard-coded, as the gateway does for the read tools.

## The UX Pilot agent

An executor with one model step, not an LLM author. Per run, in order.

**1. Theme, once per app.** Generate or select a UX Pilot theme from the
Blueprint's design-system section (personality, colour roles, type scale) and
extract the resulting tokens back into `designSystem`. This is what makes
thirty separately generated screens read as one product, and what lets a page
that fell back to A2UI sit next to a UX Pilot page without clashing.

**2. Prompt per page, from the page brief.** The existing brief already
carries the contract, the primary entity, the derived columns and form fields,
the actions, the widgets and the declared states. The agent renders that into
the generate prompt so that **Forge dictates the labels**: KPI names, column
headers, button text, empty-state copy. This is the whole basis for binding
later. Generation is per page; autoflow is not used, because a flow generated
from one prompt takes label control away.

**3. Generate through the gateway**, passing the theme id so every page shares
it.

**4. Store the result as a design source.** Type `uxpilot`, `treatAs:
specification`, one frame per generated page, keyed by the brief's content
hash. A rebuild re-projects from the store and regenerates only pages whose
brief changed, so credits are spent once per distinct brief. The design also
lives in the user's UX Pilot workspace; edits there come back through design
versions on the next sync.

**5. Strip the chrome.** UX Pilot draws its own sidebar and top bar. Forge's
layout owns those. The agent keeps the page body only, using the chrome
detection the Figma import already has.

**6. HTML to tree** through the existing Figma-layout route, which maps
semantic HTML onto the catalog's layout, text, image and form nodes.

**7. Bind by known label.** Every data-bearing region is matched to the brief:
a tile labelled with a KPI name the brief supplied becomes that widget; a
table whose headers are the brief's columns becomes a live list over the
entity; a button carrying an action label becomes that action. Because the
labels were chosen by Forge, this is a lookup. Anything that does not match is
left unbound and reported as a warning on the page. Invented literals in the
HTML are discarded, never imported, for the same reason the A2UI converter
discards the sample data model.

**8. Same gate.** The tree is validated against the component catalog, child
contracts and prop schemas exactly as an A2UI tree is, then wrapped in the
same artifact proposal.

## Failure and fallback

The user clicked UX Pilot, so a silent swap to A2UI would ignore the click,
and a hole would be worse than either. The rule:

1. A generate or gateway failure goes back through the observer and repair
   loop with findings; repair for this agent means regenerate with the
   findings appended.
2. After repair fails, the page is composed by A2UI **and marked visibly** as
   `designedBy: forge` with the reason attached to the page, so the user sees
   which pages did not come from UX Pilot and why.
3. A missing or invalid MCP configuration stops the run before any page is
   attempted; Smith reports it and asks for the configuration.

## Cost

A2UI spends Forge's tokens; UX Pilot spends the user's credits, roughly one
generation per page plus one per theme. The choice card states the estimate.
Two things keep it bounded: the content-hash store means rebuilds do not
regenerate, and Smith can suggest a tiered split (UX Pilot for dashboards and
workspaces, pattern templates for the CRUD tail) as a follow-up refinement
without changing anything above.

## The unknown that gates the design

No generate payload has been observed on any branch. Step 7 assumes the
returned HTML is semantic enough that labels are findable and regions are
separable. Before the agent is built, one session should call generate with a
real page brief, using a key allowed to spend a few credits, and read the
HTML. Two outcomes:

- Labels bind reliably: the design above stands.
- They do not: step 7 becomes a model step that turns the generated skeleton
  into catalog nodes with the brief's placeholders (`$columns`, `$actions`),
  and A2UI's placeholder filling supplies the data. Still one producer, still
  the same gate.

## Sequencing

1. Payload exploration (above). Decides the shape of step 7.
2. Contract fields: the `uiDesigner` decision and `PageContract.designedBy`,
   declared and regenerated.
3. Gateway: generate tools allowed under a `uxpilot` decision only; argument
   discovery extended to them.
4. Smith: the choice card, the decision write, the configuration prompt when
   the key is absent.
5. `page_layouts` dispatch and the UX Pilot agent, steps 1 to 8.
6. Fallback marking and the observer repair path.

## Non-goals

- A raw HTML canvas node carrying the generated markup verbatim. Pixel-exact,
  but outside the one catalog the palette, agents, projection and engine share,
  and invisible to the editor.
- UX Pilot autoflow or design collections as the unit of generation.
- Changing how a hand-drawn UX Pilot page is imported. That path stays
  read-only.
