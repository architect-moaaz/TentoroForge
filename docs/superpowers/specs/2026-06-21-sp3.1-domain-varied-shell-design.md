# SP3.1 — Domain-Varied App Shell

**Date:** 2026-06-21
**Status:** Design approved, pre-implementation
**Branch:** forge-v3
**Part of:** SP3 domain-driven-design program (sub-project 1 of 5).

## Problem

Every business app's shell looks the same — a dark left sidebar. `shell_layout_agent`
is already an LLM agent that freely emits `shell.json`, so the cause is **not** a rigid
template. It's that the agent is **anchored and under-informed**:

- `SHELL_LAYOUT_SYSTEM_PROMPT` offers 4 flavors (A–D) whose **worked examples are all
  header/sidebar admin layouts**, and a selection rule that routes every "data-heavy /
  ≥6 nav pages" app to **Flavor B (sidebar)**. LLMs copy the examples → every CRM, HR,
  ops, finance app collapses to the same sidebar frame (same effect we saw with the
  planner's CRUD examples in SP1.5-F2).
- The agent receives `plan` + `brand` (just primary/secondary hex + appName) + a domain
  profile, but **no information-architecture analysis** (which destinations are primary vs
  utility), **no design-language signal** (density / nav-style / surface), and **no
  pressure to diverge** from a generic admin sidebar.

Evidence: CRM `output/3v2f1yev` and Leave `output/17tdblyu` have near-identical `shell.json`
compositions (sidebar + N nav `Button`s + `Avatar` + search `Input` + `PageOutlet`); only the
labels differ.

## Decision: open generation + renderability guardrail (NOT a catalog)

The shell's building blocks are a small fixed set of layout primitives
(`Container`/`Row`/`Stack`/`Button` + `data-shell-region` + exactly one `PageOutlet`), so free
LLM output carries **low un-renderable risk** — unlike the page-component layer (SP1), which
needed a catalog because free generation hallucinated unregistered components. Therefore SP3.1
keeps the LLM **fully in charge of the shell's structure** and adds no archetype menu. Instead
it (a) **de-anchors** the prompt, (b) **enriches** the agent's inputs, and (c) adds a thin
**renderability guardrail** as a validate-or-repair-or-fallback safety net — the same
safety philosophy as SP1's binding pass, but with zero constraint on the creative choice.

## Components

### 1. Shell-context builder — `backend/services/shell_context.py` (new)

A pure function `build_shell_context(plan, nav_flow, design_spec, domain_context) -> str`
that produces a richer prompt block than today's bare app/brand dump:

- **Information architecture:** from `nav_flow.pages` + `plan.pages`, group destinations into
  **primary** (core workflow pages) vs **utility/admin** (settings, admin/*, users) vs
  **secondary**. Surface counts and the grouping so the agent can choose a frame that fits the
  IA (e.g. few primaries → top-bar; many grouped destinations → sectioned sidebar; a
  focus-workflow app → split workspace).
- **Design-language hints:** read whatever the `design_spec` carries about nav style, density,
  radius, surface, and type scale (produced fully by SP3.3 later; SP3.1 reads what exists and
  degrades gracefully when absent).
- **Brand character:** pull the dossier's brand-character / persona text (via the existing
  `domain_context`), not just hex colors.
- **Divergence directive:** an explicit instruction to **choose the frame the domain actually
  wants and avoid defaulting to a generic admin sidebar** unless the IA genuinely calls for one.

Pure, no I/O, fully unit-testable.

### 2. De-anchored system prompt — `backend/agents/shell_layout_agent.py`

Revise `SHELL_LAYOUT_SYSTEM_PROMPT`:

- **Remove the single-pattern anchoring.** Replace the all-sidebar worked examples with a
  **structurally diverse** set (top-bar app, sectioned-sidebar, icon-rail + content, split
  workspace, command-bar) described compactly — or describe the possibility space abstractly —
  so the model does not copy one layout. Keep at most one short *format* example (showing
  `data-shell-region` + `PageOutlet` mechanics) clearly labelled "format reference, not a
  layout to copy."
- **Keep all renderability rules verbatim:** exactly one `PageOutlet` (id `page-outlet`);
  `data-shell-region` annotations; responsive 375–1920px; nav `Button`s with Lucide `icon`;
  logo/app-name; user avatar.
- Add a one-line directive mirroring the divergence directive from the context builder.

This is a prompt-contract change; verified via content assertions + the guardrail below.

### 3. Renderability guardrail — `backend/services/shell_guardrail.py` (new)

Deterministic validator: `validate_shell(shell: dict) -> list[str]` (list of issues; empty =
valid) plus `is_renderable_shell(shell) -> bool`. Checks ONLY what the **renderer** actually
requires — never the design choice:

- exactly **one** `PageOutlet` node (id `page-outlet`) — verified against the renderer:
  `ShellWrapper` renders the shell via `PageOutletContext` and the `PageOutlet` node is the
  single hard requirement;
- every node `type` is a **registered** component (reuse `schema_prompt._registered_components()`);
- at least one navigation `Button` (a shell with no nav is unusable);
- the root is a valid PageV2 envelope.

NOTE: `data-shell-region` values are **editor metadata, not renderer-enforced** (the renderer
keys on `PageOutlet`, not region names), so the guardrail does **not** validate or constrain
region values — doing so would over-constrain the LLM's creative choice, which is exactly what
this design avoids.

A repair helper `repair_shell(shell) -> dict | None` fixes the cheap deterministic cases
(e.g. drop a duplicate `PageOutlet`); returns `None` when unrepairable (e.g. zero `PageOutlet`,
unregistered node types).

### 4. Wiring — `backend/agents/shell_layout_agent.py` + `generate.py`

- `run_shell_layout_agent` builds its user prompt via `build_shell_context(...)` (passing the
  already-available `design_spec`), instead of the current inline app/brand dump.
- After the agent returns a parsed shell, run `validate_shell`; if issues, try `repair_shell`;
  re-validate. If still invalid, **fall back to today's behavior** (return the agent's shell if
  parseable, else `None` → pages render bare). Chunking-style validate-or-fallback: the
  guardrail never makes the shell worse than today.

## Data flow

```
plan + nav_flow + design_spec + dossier
   → build_shell_context (IA groups + design-language hints + brand character + divergence)
   → shell_layout_agent (LLM freely designs the frame, de-anchored prompt)
   → validate_shell → (repair_shell if needed) → re-validate
        valid → write shell.json
        invalid → fall back (parseable shell or bare) — never worse than today
```

## Error handling

- Invalid free output → repair → fallback. Never aborts generation; worst case is today's
  behavior (bare pages), never a broken shell.
- Missing design-language fields (pre-SP3.3) → context builder omits them; the agent still
  generates from IA + brand + divergence.

## Out of scope (SP3.1)

- The **source** of the full design language (density/type-scale/surface) — that's **SP3.3**;
  SP3.1 only *consumes* what `design_spec` provides and degrades gracefully.
- Page content, dashboards, planner IA/CRUD changes — other SP3 sub-projects.
- New UI components; the Figma path (already differentiates).
- A shell-archetype catalog/menu — explicitly rejected in favor of open generation.

## Testing

- `build_shell_context`: IA grouping (primary vs utility vs secondary from nav_flow/plan);
  includes the divergence directive; includes design-language hints when present and omits
  cleanly when absent.
- `validate_shell`: passes a good shell; flags zero/duplicate `PageOutlet`, an unknown
  `data-shell-region`, an unregistered node type, a nav-less shell.
- `repair_shell`: removes a duplicate `PageOutlet`; drops an unknown-region wrapper preserving
  children; returns `None` on unrepairable input.
- Prompt: de-anchored prompt no longer contains a single repeated sidebar example; still
  contains the renderability rules (one `PageOutlet`, `data-shell-region`, responsive).
- Integration (mocked LLM): a free top-bar shell passes the guardrail and is written; a broken
  shell (two `PageOutlet`s) is repaired or falls back — never aborts.
- Live (manual, post-merge): generate two contrasting domains and confirm the shells are
  **structurally different** (e.g. a top-bar/command app vs a sectioned sidebar), not two
  identical dark sidebars.

## Success criteria

Two apps from different domains no longer share one dark-sidebar frame: the LLM picks the shell
structure the domain's IA calls for, informed by brand character and design language, and a
renderability guardrail guarantees the free output always renders — with no regression to the
existing shell pipeline when the model plays it safe.
