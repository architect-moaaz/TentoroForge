# Approval Workflow Lifecycle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the row-level Approve/Reject lifecycle work end-to-end: creating an entity starts its approval workflow → the workflow pauses at the approval node and a task is persisted → clicking Approve/Reject resolves that pending task and resumes the workflow with the decision → the entity's status is updated (and any notify/audit nodes run).

**Architecture:** The generated app already ships a workflow engine (`src/lib/workflows`), a Data Engine (`/api/data/[...path]`) that emits `<entity>_created` events, and an event-registry that bridges the two. Six seams between them are mis-wired so nothing starts, nothing is persisted on the event path, and Approve/Reject are indistinguishable no-ops. This plan aligns the naming, persists tasks on any pause, resolves+resumes by entity, and makes the binding emit distinct decisions.

**Tech Stack:** Python generation pipeline (backend/services, backend/agents) + vendored Next.js/Drizzle TS runtime (backend/templates/runtime, injected by runtime_injector.py). Backend tests: `/usr/local/bin/python3 -m pytest` from `backend/`. The TS runtime cannot be unit-tested from this repo — TS seams are verified structurally (generated-artifact assertions) and finally by an end-to-end generation run.

## Reverse-engineered contracts (verified against output/e2e-leave-bind)

- **Data Engine emit** — `src/lib/data-engine.ts` on insert: `const event = \`${entityName.toLowerCase()}_created\`; emit(event, { entityId: record.id, entity: record, user })`. Also `_updated`, `_deleted`.
- **Event-registry** — `src/lib/event-registry.ts` reads `src/contracts/event-bindings.json` (`{bindings:[{event, source, workflows:[id], conditions}]}`), and on a matching data event calls `triggerWorkflowEvent(workflowId, payload)` **passing the workflow ID as the event arg** (bug — see Seam 3).
- **triggerWorkflowEvent** (`src/lib/workflows/index.ts`) — matches workflows where `trigger.type==="api_event" && (trigger.event===eventName || workflow.name===eventName)`, runs `executeWorkflow`, and **does not persist tasks on pause** (bug — Seam 2).
- **execute route** (generated by `runtime_injector._generate_workflow_api_route`) — `triggerWorkflow(id, input, user)`; persists a `workflow_tasks` row when `result.status==="paused"`; when `taskId` present, marks that row completed with `input.__decision`. Does **not** resolve a task by entity (Seam 3).
- **executeWorkflow / resume** (`src/lib/workflows/engine.ts`) — re-runs from the trigger each call. An `approval`/`user_task` node pauses unless `ctx.variables["__step_<nodeId>_completed"]` is set, in which case it marks the step completed (reading `__step_<nodeId>_decision`, `__step_<nodeId>_completedBy`) and continues — **but does not write the node's `outputParams` from the decision** (bug — Seam 4), so a downstream `db_update` never receives approved/rejected.
- **event-bindings generation** — `services/contract_generator.py::_generate_event_bindings` only emits a binding when `plan.api_strategy[...][op]` carries `triggers_workflow` (Seam 1: usually absent → no binding → workflow never starts).
- **workflow_tasks columns** (execute route INSERT): `id, workflow_id, workflow_instance_id, node_id, node_label, task_type, status, assignee_id, assignee_role, entity_type, entity_id, form_data, form_binding, process_variables, due_at, created_at`; resume UPDATE sets `status='completed', completed_by, completed_at, decision, response_data`.
- **Binding** — approve/reject buttons currently get identical `{workflow:"<wf>", args:{id:"{{item.id}}"}}` (Seam 5).

```python
_APPROVE_WORDS = ("approve", "accept", "confirm", "grant", "authorize")
_REJECT_WORDS = ("reject", "deny", "decline", "refuse")

def annotate_decision_actions(schema: dict) -> tuple[dict, dict]:
    """Give approve/reject-labelled workflow buttons a distinct `args.__decision`
    ('approved'/'rejected') so the execute route can resolve+resume the pending
    approval task with the manager's decision. Only touches Buttons that already
    carry props.workflow; entity id args are preserved. Idempotent."""
    n = 0
    for node in iter_nodes(schema):
        if node.get("type") != "Button":
            continue
        p = node.get("props")
        if not isinstance(p, dict) or not p.get("workflow"):
            continue
        label = normalize_label(p.get("label") or p.get("text"))
        if any(w in label for w in _APPROVE_WORDS):
            decision = "approved"
        elif any(w in label for w in _REJECT_WORDS):
            decision = "rejected"
        else:
            continue
        args = p.setdefault("args", {})
        if args.get("__decision") != decision:
            args["__decision"] = decision
            n += 1
    return schema, {"decisions_annotated": n}
```

## Self-Review notes / risks

- **Identifier used in bindings vs. Seam 3a** — Task 2 must emit the workflow identifier that Task 3a's `triggerWorkflow(id)` resolves (id or name are both cache keys; prefer the file `id`). Keep them consistent.
- **Entity name casing** — Data Engine emits `${entityName.toLowerCase()}_created`; `entityName` is the registered entity slug. Task 2 must match that exact casing (verify against the registered entity name, not the PascalCase plan name).
- **No approval node** — workflows without an approval/user_task node get no created-binding (correct: nothing to resume).
- **Multiple pending tasks per entity** — Task 5 takes the most recent; acceptable for the single-approver case. Note the limitation.
- **Decision→status value** — Seam 4 sets the outputParam to the literal `approved`/`rejected`; if an entity's status enum differs, the workflow's own `db_update` mapping governs. Document that the workflow author should map the decision var to the entity status.
